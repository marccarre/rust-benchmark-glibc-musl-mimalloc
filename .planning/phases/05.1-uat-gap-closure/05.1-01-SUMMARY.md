# Phase 05.1 Plan 01: Apple Silicon Rosetta SIGSEGV Gap Closure Summary

Closes UAT Phase 5 Gap 1 (REPR-01): the Phase 3 D-09 `RUSTFLAGS=-C target-cpu=x86-64-v3` baseline emitted AVX2/BMI2 instructions that Apple Silicon's Rosetta-2 emulator cannot execute, causing all 18 cells of `just bench-all-smoke` to SIGSEGV (exit 139) on macOS arm64 hosts. Restored REPR-01 ("a fresh user follows README and reproduces the matrix") for Apple Silicon hosts via a Dockerfile ARG-with-default override, justfile auto-detect + BENCH_TARGET_CPU env-var knob, and a README §Troubleshooting entry — without breaking the v1.0 GHA invariant ("all 18 cells pass on ubuntu-24.04 with v3 codegen, default behavior unchanged").

## Outcome

A fresh Apple-Silicon user running `just bench-all-smoke` now sees the build recipe auto-emit the diagnostic line `[apple-silicon] auto-detected; using target-cpu=x86-64-v2 (override BENCH_TARGET_CPU=... to change)` on stderr, the Dockerfile builder stages compile with `-C target-cpu=x86-64-v2` (+ `+crt-static` re-appended for distroless-static and scratch), and Rosetta executes the resulting binaries cleanly. The 18 cells produce `results/{alloc}-{env}.json` files; `just aggregate` succeeds; the dashboard opens. The user can override the auto-detect explicitly via `BENCH_TARGET_CPU=...` (e.g., `x86-64-v3` to force the CI default if running on a real x86-64 Mac via Asahi-on-Linux or future Rosetta improvements). On real x86-64 Linux (CI / GHA / local), the env var is empty, the auto-detect predicate is false (`uname -m == x86_64`), the override forwarding emits `--build-arg RUSTFLAGS_OVERRIDE=""`, and the Dockerfile's `${RUSTFLAGS_OVERRIDE:-<default>}` expansion falls through to the original v3 (or v3 + crt-static) literal — bit-identical to the v1.0 CI behavior.

## Decisions Made

1. **Contract (a) — override REPLACES the entire RUSTFLAGS string.** The Dockerfile's `${RUSTFLAGS_OVERRIDE:-<default>}` expansion swaps in the entire user-supplied string when non-empty, so the justfile must re-emit `+crt-static` for distroless-static + scratch. The alternative (splitting `target-cpu` and `target-feature` into separate ENV pieces) was rejected because it doubles the Dockerfile diff and adds a second build-arg the user might forget to set. The current shape keeps the override mechanism a single ARG/ENV pair per Dockerfile; the justfile owns the "which envs need +crt-static" logic.

2. **Auto-detect predicate is intentionally narrow.** The recipe checks `uname -m == arm64 && uname -s == Darwin` (Apple Silicon macOS only). Real x86-64 Linux runners and Linux on arm64 (Graviton, Ampere, etc.) are NOT auto-detected — the latter hosts execute amd64 binaries via different emulation layers (binfmt_misc/qemu-user) which have a different instruction-set support matrix. If a user on Linux/arm64 hits a similar gap, the documented escape hatch is `BENCH_TARGET_CPU=x86-64-v2 just bench-all-smoke` — same knob, different rationale. The auto-detect's narrow scope is deliberate so the v1.0 CI behavior remains pristine on every non-Apple-Silicon host.

3. **Convenience recipe is redundant-by-design.** `just bench-all-smoke-apple-silicon` is a one-line wrapper over the auto-detect, so it produces identical behavior to plain `just bench-all-smoke` on Apple Silicon. The value is purely discoverability via `just --list` — a fresh user encountering exit 139 should see a recipe whose name matches their search query without needing to discover the env-var knob first. The README explicitly documents both paths.

## Trade-offs

- **v2 ≠ v3 byte-comparable.** Numbers from a v2-codegen Apple-Silicon run are NOT byte-comparable with v3-codegen CI runs. Documented as a reproducibility caveat in both §Troubleshooting and §Reproducibility (cross-linked). For qualitative comparison (relative ordering between allocators) the v2 run is still informative — the trade-off is acknowledged in the README rather than hidden.
- **No GHA workflow change in this plan.** The bench.yml workflow (`.github/workflows/bench.yml`) is untouched; Plan 02 of this phase owns any GHA-side change. This plan deliberately keeps its blast radius scoped to "the local-host reproduction loop on Apple Silicon"; CI continues to forward an empty `RUSTFLAGS_OVERRIDE` (auto-detect false on `ubuntu-24.04`).
- **End-to-end Docker rebuild not exercised in this worktree.** Verified the auto-detect logic via shell-trace on the planner's macOS arm64 host but did NOT trigger an actual `docker buildx build` cycle (~10-30 min × 18 cells of bandwidth). The human UAT in `.planning/phases/05.1-uat-gap-closure/05.1-04-PLAN.md` will exercise the full local rebuild and confirm 18/18 cells pass on Apple Silicon. This plan ships the mechanism + documentation; the human UAT confirms the end-to-end loop.

## Deviations from Plan

None — plan executed exactly as written. The plan's `<automated>` verify blocks for Tasks 1, 2, and 3 all passed on first attempt after the file edits. One BSD-grep portability nuance: the plan's verify regex `^ENV RUSTFLAGS="\${RUSTFLAGS_OVERRIDE:-` uses unanchored `${` mid-pattern which macOS BSD grep treats as `$`-as-end-of-line + literal `{` and refuses to match. The substantive check is the same (the Dockerfile `ENV RUSTFLAGS="${RUSTFLAGS_OVERRIDE:-...}"` line exists and uses the override pattern); switched to `grep -cF` for portable literal matching. This is a verify-script ergonomics observation, not a deviation from the plan's substance — the criterion is met. The other plan-supplied verify commands matched verbatim.
