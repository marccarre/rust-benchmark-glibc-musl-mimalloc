# Phase 05.1: Code Review Report

**Reviewed:** 2026-05-22T19:41:51Z
**Depth:** standard
**Files Reviewed:** 9

## Summary

Phase 05.1 closes two UAT gaps from Phase 05: (1) Apple Silicon Rosetta+v3 SIGSEGV via a `RUSTFLAGS_OVERRIDE` build-arg pattern across all six Dockerfiles plus a `BENCH_TARGET_CPU` justfile knob and an Apple-Silicon auto-detect, and (2) a CI fan-in path bug where `Reorganize artifacts` `mv` patterns sourced from the wrong subdirectory level and silenced their failures.

The two narrow fixes themselves are correctly implemented — the Dockerfile `${RUSTFLAGS_OVERRIDE:-default}` pattern preserves the v1.0 CI invariant when no override is supplied, the justfile auto-detect predicate is correct, the workflow `mv` paths now match the v4 upload/download artifact tree shape, and the silencing has been removed.

However, the review surfaced one **CRITICAL** documentation bug that predates Phase 05.1 but is now load-bearing for the README "Run it yourself" walk-through (the `bench-all` and `bench-all-smoke` recipes do NOT pass the warmup/duration flags the README claims, and the CLI does not even accept them on the `run-all` subcommand), plus six **WARNING**-level issues including a stale CI comment that contradicts the executed code, an inconsistent `OCI_VERSION` semantics between local and CI builds, a doubly-invoked `dive-check` in the CI matrix, two cache layers without `save-if` guards, and a hard-fail aggregate path that fires even when the upstream matrix is entirely skipped.

## Critical Issues

### CR-01: README "Run it yourself" recipes claim CLI flags that do not exist

**File:** `README.md:36-40` (cross-cuts `justfile:189-229`, `crates/alloc-bench-cli/src/main.rs:201-211`, `crates/alloc-bench-cli/src/run.rs:781-786`)
**Issue:** The README documents two recipes with concrete warmup/duration parameters:
- `just bench-all-smoke` — claimed to use `--warmup 1s --duration 5s` per scenario across 18 cells × 10 scenarios × 3 seeds
- `just bench-all` — claimed to use `--warmup 5s --duration 60s` per scenario, "the canonical statistical-quality measurement"

Three independent contradictions with the actual code:
1. **`run-all` subcommand has no `--warmup` or `--duration` flag.** `crates/alloc-bench-cli/src/main.rs:205-211` only declares `--output` and `--seed`. `crates/alloc-bench-cli/src/run.rs:781-786` hardcodes `warmup: Duration::from_secs(1), measure: Duration::from_secs(5)` inside `run_all`. There is no path by which a justfile recipe could change these values. Therefore `just bench-all` (the supposedly statistical-quality recipe) and `just bench-all-smoke` are behaviorally **identical** today.
2. **`just bench-all` runs only one seed (7), not three.** `justfile:135` invokes `run-all --output ... --seed 7` exactly once per cell. The 3-seed loop lives ONLY inside `ci-bench-cell` (`justfile:381-388`) which is invoked by GHA, not by `bench-all`. So the README's "3 seeds" claim for the smoke recipe is false for the local recipe.
3. **The "~2.5 hours, ~5 GB disk" budget for `bench-all` is therefore fictional** — the actual recipe runs the same 1s/5s/single-seed configuration as the smoke recipe, so wall-clock will be ~10 minutes (matching the smoke claim), not 2.5 hours.

This is the central reproducibility promise of the project ("Run it yourself" — README §3) and a fresh user following the README will get qualitatively different statistical confidence than promised. It also undermines the "Smoke vs full run" trade-off framed at line 40.

**Fix:** Pick one of these directions and commit to it:

(a) **Wire flags through `run-all`** (largest scope, matches README intent): add `--warmup` and `--duration` arguments to the `RunAll` clap variant in `main.rs:205-211`, plumb them into `HarnessConfig` in `run.rs:781-786`, and update the justfile `run` and `bench-all`/`bench-all-smoke` recipes to forward different values. Then the README is correct without changes.

(b) **Trim the README to the truth** (smallest scope, ships now):
```diff
- - **Smoke run (~10 min)** — `just bench-all-smoke`. Uses `--warmup 1s --duration 5s` per scenario across all 18 cells × 10 scenarios × 3 seeds. Proves the loop end-to-end and catches regressions in *relative ordering*; not a statistical-quality run on its own (the smoke recipe is below the documented sample-count floor — see `.planning/research/PITFALLS.md` §1.4).
- - **Full run (~2.5 hours, ~5 GB disk)** — `just bench-all`. Uses `--warmup 5s --duration 60s` per scenario, the canonical statistical-quality measurement. Plan ~5 GB of free disk for the per-cell `results/*.json` plus the rendered `report/`.
+ - **Local matrix (~10 min)** — `just bench-all` (or `just bench-all-smoke`; they are currently identical). Uses the run-all defaults of warmup=1s + duration=5s per scenario across all 18 cells × 10 scenarios with `--seed 7`. The 3-seed multi-run statistical-quality loop is CI-only today (GHA `bench-matrix` job → `ci-bench-cell` recipe). Proves the loop end-to-end and catches regressions in *relative ordering*; below the documented sample-count floor — see `.planning/research/PITFALLS.md` §1.4. A future `--warmup`/`--duration` plumbing pass will restore the local statistical-quality recipe.
```

The review prefers (a) because the README's existing framing is the better long-term contract — but (b) is the correct minimum to ship before the next time a fresh user follows REPR-01. CLAUDE.md `## Conventions` states `bench-all-smoke` is `--warmup 1s --duration 5s` and `bench-all` is `--warmup 5s --duration 60s`; CLAUDE.md is also stale and must be updated to match whichever direction is chosen.

### WR-02: `OCI_VERSION` semantics diverge between local justfile and CI workflow

**File:** `justfile:98` vs `.github/workflows/bench.yml:177`
**Issue:** Two different sources of truth for the OCI image version label:
- Local `just build`: `OCI_VERSION=$(grep -m1 '^version' crates/alloc-bench-cli/Cargo.toml | cut -d'"' -f2)` — yields a semver like `0.1.0`.
- CI `docker/build-push-action@v6`: `OCI_VERSION=${{ github.ref_name }}` — yields a branch name (`main`, `feat-foo`), a PR ref (`123/merge`), or a tag (`v1.0`).

The OCI annotation `org.opencontainers.image.version` is supposed to be the package version per the OCI spec (semver-shaped). A consumer pulling the CI-built image and reading the version label will see something like `main`, which is not version metadata. The local build is closer to spec; CI is wrong-shape but never breaks anything because nothing parses the label downstream today.
**Fix:** Mirror the local justfile logic in CI by computing the version from `crates/alloc-bench-cli/Cargo.toml` in a step before `build-push-action`:
```yaml
      - name: Compute OCI_VERSION
        id: ociv
        run: echo "version=$(grep -m1 '^version' crates/alloc-bench-cli/Cargo.toml | cut -d'\"' -f2)" >> "$GITHUB_OUTPUT"
      - name: Build image
        ...
          build-args: |
            ...
            OCI_VERSION=${{ steps.ociv.outputs.version }}
```
Or — if the CI-shape (branch/PR ref) is intentional — set the local justfile to also use git ref so the two paths converge. Either direction is fine; the bug is the divergence.

### WR-03: `dive-check` runs twice per cell in CI

**File:** `.github/workflows/bench.yml:185-186` + `justfile:368`
**Issue:** The CI workflow has an explicit `Dive image-size gate` step (`bench.yml:185-186`) that runs `just dive-check ${{ matrix.env }} ${{ matrix.alloc }}`. Then the next step runs `just ci-bench-cell ${{ matrix.env }} ${{ matrix.alloc }}` (`bench.yml:194`), which itself contains `just dive-check {{env}} {{alloc}}` at `justfile:368`. So `dive --ci` runs against the same image twice per cell, doubling that step's wall-clock and adding ~1-3 minutes per cell × 18 cells. With the documented 60-min p95 budget this is significant.
**Fix:** Remove one of the two invocations. The cleanest direction is to drop `dive-check` from `ci-bench-cell` (since the workflow has its own explicit gate step that's clearer in the GHA UI) — but that breaks `just ci-bench-cell debian-slim ptmalloc` on a developer's laptop, where it currently provides one-stop CI parity. Better:
```diff
 # justfile:364
 ci-bench-cell env alloc:
     #!/usr/bin/env bash
     set -euo pipefail
     just build {{env}} {{alloc}}
-    just dive-check {{env}} {{alloc}}
+    # dive-check is invoked by the workflow as a separate step; skip here when
+    # CI=true to avoid double-execution. Local-laptop runs still get the gate.
+    if [ "${CI:-false}" != "true" ]; then
+        just dive-check {{env}} {{alloc}}
+    fi
     mkdir -p results meta
```
GHA sets `CI=true` automatically. Pure local invocations get the gate; CI gets it once.

### WR-04: Hard-fail Reorganize step swallows the "all upstream cells failed" signal

**File:** `.github/workflows/bench.yml:241-247` + `bench.yml:214,220` (`needs:` + `if: always()`)
**Issue:** With `if: always()` and `needs: bench-matrix`, the aggregate job runs even when bench-matrix is entirely skipped (e.g., pre-bench failure → bench-matrix skipped → aggregate runs anyway). Plan 05.1-02 deliberately removed `2>/dev/null || true` from `mv artifacts/results/*.json results/` so genuine path-drift fails loudly. Correct intent. But this same mv now also hard-fails when zero cells uploaded (e.g., all 18 cells crashed with `if-no-files-found: error` on upload). The new failure mode is indistinguishable from the bug it was added to detect: both surface as "mv: cannot stat" in the workflow log.

The `ls -la artifacts/` debug print (line 244) was added to make this self-documenting, but only fires if the directory exists. If `actions/download-artifact@v4` finds zero matches, `./artifacts` may or may not be created — the debug print itself becomes the failure point rather than the smoke gun.

This was foreseen by Plan 05.1-02 ("when zero cells succeed... `mv` will fail with No such file or directory. This is the DESIRED behavior") but the consequence is that in production, an "all 18 cells failed" outcome triggers an aggregate failure that masks the upstream truth.
**Fix:** Add a count-based gate before `mv` so the failure mode distinguishes the two cases:
```diff
       - name: Reorganize artifacts (results/ + meta/)
         run: |
           mkdir -p results meta
           ls -la artifacts/ || true   # debug print only; never fails the step
+          shopt -s nullglob
+          n_results=$(ls -1 artifacts/results/*.json 2>/dev/null | wc -l | tr -d ' ')
+          n_meta=$(ls -1 artifacts/meta/*.json 2>/dev/null | wc -l | tr -d ' ')
+          if [ "$n_results" -eq 0 ] || [ "$n_meta" -eq 0 ]; then
+              echo "::error::No artifacts to aggregate (results=$n_results meta=$n_meta). Likely upstream bench-matrix failure or path-drift."
+              exit 1
+          fi
           mv artifacts/results/*.json results/
           mv artifacts/meta/*.json    meta/
           ls -la results/ meta/
```
The hard-fail still happens; the workflow log now distinguishes "path drift" from "upstream cells failed".

### WR-05: `pre-bench` and `aggregate` cache layers lack `save-if` guards

**File:** `.github/workflows/bench.yml:92-94, 226-228`
**Issue:** The `bench-matrix` job already learned the cache-budget lesson from Phase 5 review WR-01 (commit `25bef62 fix(05): remove redundant actions/cache@v4 layer (WR-01)`) and gates its `Swatinem/rust-cache@v2` save with `save-if: ${{ github.ref == 'refs/heads/main' }}` (line 158). The other two jobs (`pre-bench` at line 92-94, `aggregate` at line 226-228) declare `Swatinem/rust-cache@v2` but omit `save-if`.        - uses: Swatinem/rust-cache@v2


### IN-02: `chmod 0777 results` is documented but still permission-sloppy

**File:** `justfile:126, 370`
**Issue:** Two recipes (`run` and `ci-bench-cell`) chmod the host `results/` dir to 0777 to allow `distroless:nonroot` (UID 65532) to write its output files. Documented in adjacent comments and in distroless-cc.Dockerfile:62. Functional and well-understood, but world-writable on a multi-user host is unnecessary — `chmod 0777` because UID 65532 ≠ host UID is overbroad. A tighter alternative is `chmod 0707` (owner can do anything, group blocked, others can write/read/execute) or `chown 65532:0 results` if the host has root, or `--user $(id -u):$(id -g)` on the docker run plus a writable tmpfs for the bench output. Any of these is more principled, but on a single-user dev box the current approach is harmless. Flagged so it's reviewed when the project moves to multi-user CI runners.
**Fix:** Defer; revisit when adding self-hosted runners.

### IN-03: `awk` interpolation of `$SIZE_BYTES` is shell-injection-shaped though benign today

**File:** `justfile:372`
**Issue:** `SIZE_MB=$(awk "BEGIN { printf \"%.2f\", $SIZE_BYTES / 1024 / 1024 }")` interpolates `$SIZE_BYTES` directly into the awk script. The value comes from `docker image inspect ... --format '{{.Size}}'` (line 371), which returns an integer for a healthy image — so this works. But if `docker image inspect` ever returned an empty string (image missing — but `set -e` would catch that earlier) or a non-integer (impossible per Docker contract), the awk script would throw a parse error. The pattern is `command-substitution-into-script-string`, which is an anti-pattern even when the input is constrained.
**Fix:** Pass the value as an awk variable instead of interpolating into the script:
```diff
-    SIZE_MB=$(awk "BEGIN { printf \"%.2f\", $SIZE_BYTES / 1024 / 1024 }")
+    SIZE_MB=$(awk -v b="$SIZE_BYTES" 'BEGIN { printf "%.2f", b / 1024 / 1024 }')
```
Same arithmetic, no string interpolation, no parse-error footgun.

### IN-04: `wagoodman/dive:latest` is unpinned in the justfile fallback

**File:** `justfile:281`
**Issue:** `docker run --rm ... wagoodman/dive:latest --ci ...` uses the floating `:latest` tag. Project conventions explicitly forbid floating tags ("`docker buildx imagetools inspect cgr.dev/chainguard/wolfi-base@<floating tag>` ... pin manifest-list digest" — `docker/wolfi.Dockerfile:7-13`). The `dive` fallback is a CI gate (`dive-check`); a silent base-image change between runs could cause `dive --ci` thresholds to start failing for non-source-code reasons. Pre-existing issue (not introduced in 05.1) but worth flagging since `dive-check` is in the changed file list.
**Fix:** Pin to a digest or a specific tag:
```diff
-            wagoodman/dive:latest \
+            wagoodman/dive:v0.13.1 \
```
or even better, pin to a digest the way `wolfi.Dockerfile` does.

### IN-05: README "six libc·environment combinations" is inconsistent with the 18-cell matrix

**File:** `README.md:5, 22`
**Issue:** README tagline (line 5): "six libc·environment combinations × ten workload scenarios". Line 22: "across four allocators, six libc·env combinations, and ten workload scenarios". The matrix has 6 environments × 3 allocators = 18 cells (not 6); the explicit table at line 67-86 shows 18 rows. "Six libc·environment combinations" is accurate only if you mean "six environments × N allocators" — the prose is ambiguous and a fresh reader will count the table and find 18, not 6.
**Fix:** Disambiguate:
```diff
- > Reproducible Rust allocator benchmarks across glibc/ptmalloc, musl/mallocng, jemalloc, and mimalloc — six libc·environment combinations × ten workload scenarios.
+ > Reproducible Rust allocator benchmarks across glibc/ptmalloc, musl/mallocng, jemalloc, and mimalloc — eighteen meaningful (env × allocator) cells across six runtime environments × ten workload scenarios.
```
Same fix at line 22.
