<objective>
Make `report/index.html` legible on a typical 1440px-wide screen. The screenshot
evidence shows six concrete failures: chart titles are clipped by the Plotly
modebar, the latency-heatmap Y-axis labels are cut off on the left, the A/B
chart's X-axis labels are clipped at the bottom, the RSS chart is dominated by
a 180-entry legend that squeezes the plot area to ~30% of the card, the
chart cards are too short, and the modebar visually overlaps the chart title
on first hover.

This is a **template-only** fix. The aggregator's data pipeline, sidecar
schema, multi-run statistics, and Phase-3 winner contract all stay
byte-identical. We touch ONLY layout primitives (margins, heights, the JS
helper that builds RSS traces) plus a handful of locked-down regression
asserts in the smoke test.

Purpose: the dashboard is the headline deliverable of the v1.0 milestone; an
illegible dashboard undermines the project's "every result is reproducible,
environment-labelled, and visually comparable" core value.

Output:
- Layout/margin/height fixes in `templates/index.html.tmpl` so titles, axis
  labels, and tick labels are not clipped at the documented 1440px page width.
- A concrete RSS-series-cap strategy: the RSS chart restricts itself to the
  TWO `(alloc, env)` cells currently chosen in the A/B picker (the user
  already nominated those as "interesting"), with a `(showing N of M cells)`
  hint and a fallback to the multi-select when A=B.
- New regression asserts in `crates/alloc-bench-aggregator/tests/smoke.rs`
  pinning the new margin/height numbers and the RSS-cap behaviour.

The RSS chart's 180-series legend is fundamentally unreadable as a single
line plot — every `(alloc, env)` x scenario combination gets its own series.
Even after the layout fixes from Task 1, plotting 180 lines in a 720x480px
card cannot work.

Concrete strategy (chosen over alternatives like top-N-by-variance,
small-multiples, or hiding the chart): **restrict the RSS chart to the
cells nominated by the A/B picker.** The user already chose those as
"interesting" via the existing `readAbSelections()` helper at the bottom of
the page; reusing the existing UI element avoids adding a new control.
Behaviour:
1. Read `readAbSelections()` to get `{a:{alloc,env}, b:{alloc,env}}`.
2. Filter `filtered` to runs where `(alloc, env)` matches A OR B.
3. If A and B are the same cell (degenerate config), fall through to the
   existing multi-select behaviour (same as before this fix), capped at
   the first 12 series alphabetically. This preserves utility when the user
   has not yet differentiated A from B.
4. Render the resulting traces (each scenario for each chosen cell still
   gets its own line — that is the whole point of the chart).
5. Add a hint annotation to `rssLayout` showing
   `(showing N of M cells — adjust A/B below to pick others)` so the user
   knows the cap exists and where to change it. Annotation goes in
   `rssLayout.annotations` per the standard Plotly contract.

Edit A (template) — replace the body of `function makeRssLines(filtered) {`
with the cell-restricted version:
```javascript
function makeRssLines(filtered) {
  const ab = readAbSelections();
  const aKey = ab.a.alloc + '|' + ab.a.env;
  const bKey = ab.b.alloc + '|' + ab.b.env;
  const sameCell = aKey === bKey;
  let candidates;
  if (sameCell) {
    // Degenerate A==B → fall back to first 12 cells alphabetically.
    const seen = new Set();
    const ordered = filtered.slice().sort((a, b) => {
      const ka = a.build.allocator + '|' + envLabel(a) + '|' + a.scenario.name;
      const kb = b.build.allocator + '|' + envLabel(b) + '|' + b.scenario.name;
      return ka < kb ? -1 : ka > kb ? 1 : 0;
    });
    candidates = [];
    for (const r of ordered) {
      const k = r.build.allocator + '|' + envLabel(r);
      if (!seen.has(k) && seen.size < 12) {
        seen.add(k);
      }
      if (seen.has(k)) {
        candidates.push(r);
      }
    }
  } else {
    candidates = filtered.filter(r => {
      const k = r.build.allocator + '|' + envLabel(r);
      return k === aKey || k === bKey;
    });
  }
  const sorted = candidates.slice().sort((a, b) => {
    const ka = a.build.allocator + '|' + envLabel(a) + '|' + a.scenario.name;
    const kb = b.build.allocator + '|' + envLabel(b) + '|' + b.scenario.name;
    return ka < kb ? -1 : ka > kb ? 1 : 0;
  });
  const traces = [];
  for (const r of sorted) {
    const samples = r.metrics.rss_growth_samples || [];
    if (samples.length === 0) { continue; }
    traces.push({
      type: 'scatter',
      mode: 'lines',
      name: legendName(r) + '·' + r.scenario.name,
      x: samples.map(s => s.t_s),
      y: samples.map(s => s.rss_kb),
      line: { color: ALLOC_COLORS[r.build.allocator] || '#888' },
    });
  }
  return traces;
}
```
This preserves the alphabetical sort contract (alloc | env | scenario) — the
byte-identical-output discipline still holds because the input set is
deterministic given a fixed A/B selection, and the JS render path is
client-side only (it never feeds back into REPORT.md).
