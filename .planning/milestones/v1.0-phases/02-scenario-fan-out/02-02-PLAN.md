The `parallel_merge_sort` helper function (private, module-level) per RESEARCH.md §CPU-bound "Implementation skeleton":
```rust
fn parallel_merge_sort<T: Ord + Send + Copy>(slice: &mut [T]) {
    if slice.len() <= 1024 {
        slice.sort_unstable();
        return;
    }
    let mid = slice.len() / 2;
    let (left, right) = slice.split_at_mut(mid);
    rayon::join(|| parallel_merge_sort(left), || parallel_merge_sort(right));
    // MERGE STEP — allocations land HERE (in the critical path):
    let mut merged: Vec<T> = Vec::with_capacity(slice.len());
    let (mut i, mut j) = (0, 0);
    while i < left.len() && j < right.len() {
        if left[i] <= right[j] { merged.push(left[i]); i += 1; }
        else { merged.push(right[j]); j += 1; }
    }
    merged.extend_from_slice(&left[i..]);
    merged.extend_from_slice(&right[j..]);
    slice.copy_from_slice(&merged);
}
```

Per RESEARCH.md §Pitfall 4: the `Vec::with_capacity(slice.len())` inside the merge step is intentional — allocating a temp buffer once at the top would defeat the benchmark by removing allocations from the critical path. CONTEXT.md confirms: "Allocations land in the critical path so the allocator's lock contention shows up."

Per RESEARCH.md §"Why par_sort_unstable is wrong": do NOT use `<[T]>::par_sort_unstable()` — it has pre-allocated buffers and no allocations in the hot path.

  let mut short: Vec<Box<[u8]>> = Vec::with_capacity(self.cfg.allocs_per_tick as usize);

> Per `.planning/config.json`, no `security_enforcement` flag (defaults to absent → disabled). Threat-model section included for visibility.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| In-process axum server ↔ in-process reqwest client | Both inside our process via 127.0.0.1 loopback. Same global allocator. No external network exposure. Localhost binding `127.0.0.1:0` (OS picks port) means no inbound exposure even temporarily. |
| tokio runtime task boundary | Server task runs in background, fire-and-forget. Server-task panic would NOT propagate to scenario `tick()` — but `axum::serve(...).await.unwrap_or_else(|e| eprintln!(...))` swallows it silently to avoid runtime panic. The scenario's `tick()` will see request failures (reqwest errors) instead. |
| rayon scoped pool ↔ global pool | Scoped pool isolates this scenario's threads from other rayon users in the same process (matters for run-all where multiple scenarios share a process). |
| Long-lived `self.long_lived` ↔ short-lived per-tick `short` | Ownership boundary enforced by Rust — no sharing, no leaks. Eviction at cap prevents unbounded growth. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-Bind | Denial of Service | Web scenario port binding fails (port exhaustion under run-all) | mitigate | `127.0.0.1:0` lets OS pick any free port; reqwest client targets the captured `local_addr`. Each `Web` instance uses its own port. |
| T-02-02-RT | Tampering | tokio Runtime per tick (instead of once in setup) would dominate the latency histogram | mitigate | RESEARCH.md §Pitfall 1 hard rule. Implementation uses `Option<Runtime>` field populated in `setup()` only. Verify in source review. |
| T-02-02-Frag | Denial of Service | Fragmentation-soak unbounded `long_lived` growth → OOM-kill | mitigate | `long_lived_cap` config field (default 10_000) + `swap_remove` random eviction per RESEARCH.md §Pitfall 8. Plan 03 smoke verifies peak_rss stays bounded. |
| T-02-02-Rayon | Tampering | Global rayon pool corruption across scenarios in run-all | mitigate | Scoped `rayon::ThreadPool::new()` per RESEARCH.md §CPU-bound. Each CpuBound scenario instance owns its pool; never touches the global pool. |
| T-02-02-DCE | Tampering | LLVM elides allocations in `--release` | mitigate | Mid-buffer write + `std::hint::black_box` per Phase-1 PITFALLS §1.2 — applied in every scenario. Plan 03 adds the LLVM-IR grep gate. |
| T-02-02-SC | Tampering | axum/tokio/reqwest/rayon installs | mitigate | All in CLAUDE.md mandate + verified in RESEARCH.md Package Legitimacy Audit. No checkpoint:human-verify needed per RESEARCH.md disposition. |
