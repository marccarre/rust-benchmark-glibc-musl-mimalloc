# Phase 4 — UI Design Contract

> Visual and interaction contract for the static `report/index.html` Plotly dashboard, the `report/REPORT.md` markdown report, and the `README.md` system diagram. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Artifact shape (LOCKED in 04-CONTEXT.md):** a single self-contained `report/index.html` rendered from `crates/alloc-bench-aggregator/templates/index.html.tmpl` by `tinytemplate` 1.x with a single `{results_json}` placeholder. Plotly.js loaded from a pinned CDN URL (D-02). Vanilla-JS multi-select sidebar (D-03). Four charts (D-04). No bundler, no npm, no React/Vue/Svelte, no design system. Audience: technical readers (Rust engineers / SREs) viewing locally via `file://` after `just aggregate`. The HTML is openable by double-click; PR reviewers commonly screenshot it.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — single static HTML page emitted by Rust + `tinytemplate` |
| Preset | not applicable (no React/Next.js/Vite — shadcn gate inapplicable per gsd-ui-researcher) |
| Component library | none — native HTML elements only (`<select multiple>`, `<table>`, `<details>`) |
| Icon library | none — Unicode glyphs only (⚠ U+26A0, ✓ U+2713, ◐ U+25D0). Avoids any external font / icon dep so `file://` works offline |
| Font | system stack: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif` for body + UI; `ui-monospace, "SF Mono", Menlo, Consolas, monospace` for IDs / numbers / SHA-1 hashes |

**Why no design system:** The "frontend" is a one-page artifact with ~150 lines of inline JS (D-03), zero build step, and no install. A design system would add toolchain weight that violates the project's "open via `file://`, zero server" contract (AGG-01). System fonts give consistent, fast, offline-safe rendering across macOS / Linux / Windows screenshots.

## Spacing Scale

Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline gaps inside sidebar select rows; legend swatch ↔ label |
| sm | 8px | Padding inside `<select>`; row spacing inside the chart legend |
| md | 16px | Default block spacing; padding inside chart cards; sidebar internal padding |
| lg | 24px | Sidebar ↔ main pane gap; gap between rows of the 2×2 chart grid |
| xl | 32px | Page-level top padding; gap between the chart grid and the bottom A/B diff section |
| 2xl | 48px | Header ↔ first content section gap |
| 3xl | 64px | Reserved — not used in v1 (single-page report has no major section breaks needing this) |

**Exceptions:** none. The `<select multiple>` browser-native element has user-agent default padding that may not be a multiple of 4; we accept the user-agent default rather than override it (overriding it produces inconsistent behaviour across Chromium / Firefox / Safari). All other paddings, margins, gaps are from this scale.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.3 |
| Display | 28px | 600 | 1.2 |

**Roles in this artifact:**

- **Body (14px / 400 / 1.5):** all paragraph text, table cells, sidebar option text, footnote text. 14px (not 16px) is the right default for a data-dense developer dashboard — it lets four Plotly charts + a sidebar + a diff section fit on a single 1440-wide laptop screen without scroll, which is the canonical viewing configuration.
- **Label (14px / 600 / 1.4):** sidebar section headings ("Scenarios", "Environments", "Allocators"), table column headers, A/B picker labels ("Config A" / "Config B"), legend titles inside Plotly charts (overridden via Plotly's `font` config).
- **Heading (20px / 600 / 1.3):** chart card titles ("Throughput by scenario", "Latency percentiles", "RSS over time", "A/B comparison"), section headings inside REPORT.md when rendered as HTML.
- **Display (28px / 600 / 1.2):** the single page `<h1>` ("alloc-bench report — {N} runs across {M} cells, {date}"). Used exactly once.

**Plotly chart fonts:** Plotly's default font is `"Open Sans"` which is not bundled. Override `layout.font.family` to the system font stack above so charts render the same as the surrounding HTML — no FOUC, no broken-glyph fallback in screenshots.

**Mermaid (in REPORT.md & README.md):** Mermaid's default font is `"trebuchet ms"`; in this project Mermaid renders inside GitHub-flavoured-markdown viewers (GitHub web, VS Code preview), so we accept the renderer's default theme font rather than override it. Mermaid runs server-side on GitHub's render pipeline; we do not embed Mermaid.js into our `report/index.html`.

## Color

> 60 / 30 / 10 split adapted for a data-dense developer dashboard. The "accent" budget belongs almost entirely to chart data (allocator series colors, suspect markers, winner highlights). The chrome (sidebar, header, body text) is intentionally low-chroma so the data carries the visual weight.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background; chart card backgrounds; main pane behind charts. |
| Secondary (30%) | `#F4F5F7` | Sidebar background; table-header row; alternating-row striping inside REPORT.md tables when rendered as HTML; chart-card border `#E1E4E8` (1px) sits on top of this. |
| Accent (10%) | `#0969DA` | **Reserved for: (1) the Plotly toolbar hover-mode highlight, (2) the active-state outline of focused `<select multiple>` options, (3) inline links inside REPORT.md, (4) the "Config A" / "Config B" picker focus ring.** Never used for chart series, never for body text, never for table cell highlighting. |
| Destructive | `#CF222E` | Reserved for: (1) the ⚠ suspect badge text + icon when a run violates the suspect threshold (D-07: `samples_count < 10_000` OR `warmup_duration_s < 5.0`), (2) the "Skipped Inputs" section heading in REPORT.md (D-08), (3) error messages in the empty-state pane. **Never used as a chart series color** (would overlap meaning with allocator data). |

**Accent reserved for:** Plotly hover-toolbar highlight, focused multi-select option outline (`outline: 2px solid #0969DA`), markdown links, A/B picker focus ring. Explicitly NOT for: chart bars, chart lines, table-cell winner highlight, empty-state heading.

**Destructive reserved for:** the suspect ⚠ badge, the "Skipped Inputs" heading, fatal-error empty-state copy ("No results found matching pattern…"). Phase 4 has no destructive user actions (no delete, no overwrite confirmation) — the aggregator is a one-shot read-only batch process.

### Chart palette (separate from the chrome 60/30/10 split)

> Chart series colors are a separate concern from page chrome. We declare them here because they are part of the visual contract, but they are NOT counted in the 60/30/10 budget — they belong to the data, not the design system.

**Palette: Viridis (Plotly built-in `colorscale: 'Viridis'`)** — colorblind-friendly per the D-19 "Claude's Discretion" recommendation in 04-CONTEXT.md. Specifically:

| Allocator | Viridis-derived series color | Hex |
|-----------|-----------------------------|-----|
| ptmalloc  | Viridis stop 0.0 (deep purple) | `#440154` |
| mallocng  | Viridis stop 0.33 (teal)       | `#3B528B` |
| jemalloc  | Viridis stop 0.66 (green)      | `#21908C` |
| mimalloc  | Viridis stop 1.0 (yellow-green)| `#5DC863` |

Order is alphabetical-stable so the legend ordering is deterministic across runs (supports the D-09/D-10 byte-identical-output contract). When fewer than 4 allocators are present in a given filter view, the same hex codes are reused — never re-mapped — so a screenshot of "ptmalloc vs jemalloc" matches the same colors as a screenshot of "all four".

**Heatmap colorscale (latency-percentile chart, D-04 #2):** `Viridis` continuous scale; lower = darker (better latency = darker), higher = brighter. Add a colorbar with title "latency (ns)".

**Why Viridis over Plotly's default `Set2`:**
- Perceptually uniform across colorblind types (deuteranopia, protanopia, tritanopia).
- Sequential (works for the heatmap) AND categorically distinguishable at 4 stops (works for the bar/line series).
- Survives black-and-white print/photocopy ordering (Set2 does not).

### Per-row winner highlight

Per D-09 the per-scenario throughput-winner gets a **bold + ✓ prefix** in REPORT.md and a green-tinted cell in the HTML rendering of the same table:

| State | Color |
|-------|-------|
| Winner cell background | `#DAFBE1` (very light green tint, WCAG AA against 14px/400 body text) |
| Winner cell text | `#1A7F37` (matching mid-green; passes WCAG AA on the tinted background) |
| Winner ✓ prefix | `#1A7F37` |

These greens are NOT in the 60/30/10 chrome budget — they are a semantic "winner" signal scoped to comparison tables, used at most once per row per scenario (~6 cells visible at any time on screen). They do NOT compete with the Viridis chart palette because they appear only in tables, never inside charts.

### Suspect-run badge

Per D-07 a run is suspect if `harness.samples_count < 10_000` OR `harness.warmup_duration_s < 5.0`.

| Surface | Visual |
|---------|--------|
| HTML chart legend | `⚠ jemalloc-alpine` (the ⚠ glyph is `#CF222E` destructive color; the rest of the label inherits body color `#1F2328`) |
| HTML A/B picker option label | `⚠ jemalloc-alpine (low samples)` — extra parenthetical states the failing predicate |
| HTML hover tooltip | "Suspect run: {reason}, e.g. `samples_count=4321 < 10000` or `warmup_duration_s=2.0 < 5.0`. See REPORT.md → Skipped Inputs." Native HTML `title=` attribute (no JS tooltip library). |
| REPORT.md table row | trailing italic `*(⚠ suspect: low samples)*` — exact wording from D-07 |
| REPORT.md "Skipped Inputs" section | section heading rendered in destructive `#CF222E`; per-file row lists the file path + parsed reason |

**Why ⚠ + tooltip and not a coloured row:** the chart series color is reserved for allocator identity (Viridis palette). Tinting a series row in destructive red would conflate "allocator = X" with "this run is suspect" — two different signals. The badge is a prefix glyph + tooltip, leaving the series colour intact.

### Deferred to v2

- **Dark mode** — single-page report viewed `file://` is overwhelmingly screenshotted and pasted into PR reviews / docs whose backgrounds are light. Dark-mode adds complexity (Plotly's `template: "plotly_dark"`) and a media-query branch. Defer to v2 along with `--inline-plotly` (D-02) and the `--theme dark` flag.
- **Per-allocator brand color** (e.g. mimalloc-blue, jemalloc-green to match upstream branding) — Viridis is colorblind-safe and brand-neutral, which serves a comparison report better than vendor branding. Revisit only if user feedback specifically asks for it.

## Copywriting Contract

> The report is a single batch artifact, not an interactive app. There is no "primary CTA" in the conventional sense — the `<select multiple>` filters are the only interactive controls, and the only state transitions are filter changes (no save, no delete, no submit). Below maps each copywriting slot to the closest analogue for this artifact.

| Element | Copy |
|---------|------|
| Page `<title>` | `alloc-bench report — {run_count} runs, {timestamp}` (exact format; ASCII em dash) |
| Page `<h1>` (Display) | `alloc-bench report` (Display 28/600/1.2; subtitle line in Body 14/400/1.5: `{run_count} runs across {cell_count} cells · generated {ISO-8601 UTC timestamp}`) |
| Sidebar section heading 1 | `Scenarios` (Label 14/600/1.4) |
| Sidebar section heading 2 | `Environments` |
| Sidebar section heading 3 | `Allocators` |
| Sidebar instruction (sub-label, Body 14/400, color `#656D76`) | `Hold Cmd or Ctrl to multi-select. Charts update live.` |
| Initial-state filter selection | **All options selected by default** so all charts render with all data on first paint. The user removes filters to narrow; this matches a benchmark-comparison reading flow ("show me everything, then let me cut by axis"). |
| Empty-filter state (HTML — user has deselected every option in a category) | Heading: `No data in current filter` · Body: `Select at least one scenario, environment, and allocator to render charts.` (Body color `#656D76`, 14/400/1.5) |
| Empty-input state (HTML — aggregator shipped a report with zero runs; this should be impossible since aggregator exits non-zero per D-08, but render defensively) | Heading: `No results found.` · Body: `Run \`just bench-all\` (or \`just bench-all-smoke\` for a fast pass), then re-run \`just aggregate\`.` |
| Empty-input state (CLI — D-08 zero-glob path) | stderr: `error: no results found matching pattern "{pattern}"` · exit code: non-zero |
| Partial-failure CLI message (D-08) | stderr per file: `warn: skipped {path}: {reason}` · final stderr summary: `aggregated {N} runs, skipped {M}` · exit 0 |
| A/B picker label A | `Config A` (Label 14/600) — default selection: alphabetically-first allocator + alphabetically-first env |
| A/B picker label B | `Config B` — default selection: alphabetically-second allocator + same env as A (so the diff is allocator-only on first paint) |
| A/B picker hint (Body 14/400, `#656D76`) | `Diff = ((B − A) ÷ A) × 100%. Positive bars favor B.` |
| Chart 1 title (Heading 20/600) | `Throughput by scenario` (subtitle Body 14/400 `#656D76`: `Bars colored by allocator, faceted by environment. Y-axis unit per scenario (req/s, ticks/s, iters/s).`) |
| Chart 2 title | `Latency percentiles (heatmap)` (subtitle: `Rows = allocator·env. Columns = p50, p95, p99, p999, max. Color = nanoseconds (lower = darker).`) |
| Chart 3 title | `RSS over time` (subtitle: `One line per allocator·env tuple. Faceted by scenario. Sampled every 1s during measurement.`) |
| Chart 4 title | `A/B comparison` (subtitle: `Percent delta of throughput, p99 latency, and peak RSS between Config A and Config B.`) |
| Suspect-badge tooltip text | `Suspect run: samples_count={N} < 10000 OR warmup_duration_s={S} < 5.0. See REPORT.md → Skipped Inputs.` (one of the two predicates filled in based on actual cause) |
| REPORT.md `<h1>` | `# alloc-bench REPORT` |
| REPORT.md schema-version comment (top of file, optional per "Claude's Discretion" 04-CONTEXT.md) | `<!-- schema_version: 1 · generated by alloc-bench-aggregator vN.N.N at YYYY-MM-DDTHH:MM:SSZ -->` (recommended yes — supports forward bisect) |
| REPORT.md per-scenario allocator table heading | `## {scenario_name}` (one section per scenario; alphabetical scenario order for byte-identical output per D-09) |
| REPORT.md Docker comparison-table heading | `## Docker runtimes` |
| REPORT.md Mermaid diagrams section heading | `## Allocator architectures` (with four `### {name}` subsections in alphabetical order: jemalloc, mallocng, mimalloc, ptmalloc — alphabetical so the diagram order is deterministic and screenshots remain stable) |
| REPORT.md recommendations heading | `## Recommendations by workload` |
| REPORT.md skipped-inputs heading (only present if D-08 partial-failure occurred) | `## Skipped inputs` (rendered in `#CF222E` when displayed in HTML preview) |
| README.md system-diagram heading | `## How memory allocation works on Linux` (D-13: inserted directly after `# rust-benchmark-glibc-musl-mimalloc` H1, before any other content; Phase 5 will append "Run it yourself" below this section) |
| README.md system-diagram intro paragraph | One paragraph, ~80 words, exact tone: "When a Rust program calls `Vec::new()` or `Box::new(x)`, the request travels through `std::alloc` → the configured `#[global_allocator]` (jemalloc / mimalloc / system) → libc malloc (ptmalloc on glibc, mallocng on musl) → the kernel's `mmap` / `brk` / `sbrk` → physical memory. Each layer can change the cost, fragmentation profile, and tail-latency shape of an allocation. This benchmark measures those differences across four allocators, six libc·env combinations, and eleven workload scenarios." (The exact wording is locked here so plan-phase / executor copies it verbatim — supports the byte-identical-README contract for Phase 4.) |

**No destructive confirmations** — this phase has no destructive user actions. The aggregator is read-only, the HTML is view-only.

**No primary CTA** — the report has no submit / save / publish flow. The closest analogue is the user opening the file (which has no UI surface inside the page).

## Multi-Select Interaction Contract

> Three `<select multiple size="6">` elements per D-03. Plain HTML, no JS framework. The interaction contract below covers the corners that `<select multiple>` itself does not specify and that screenshots / reviewers may exercise.

| Behavior | Specification |
|----------|---------------|
| Initial state | **All options selected** in all three multi-selects. First paint shows all charts populated with all runs. Rationale: a benchmark report's first impression must be "I see everything"; deselect-to-narrow is the natural reading flow. |
| Selection change handler | `change` event on each `<select multiple>` calls a single `onFilterChange()` JS function which: (1) reads current selections from all three selects via `Array.from(select.selectedOptions, o => o.value)`, (2) filters the inlined `RESULTS` array, (3) calls `Plotly.react(divId, traces, layout)` for each of the four chart divs — `Plotly.react` reuses existing chart DOM, so re-render is fast and there is no re-mount flicker. |
| Empty-selection (any one of the three is empty) | Charts render the empty-state heading + body copy from the Copywriting Contract (`No data in current filter` / `Select at least one scenario, environment, and allocator…`). Plotly is NOT called with empty data; instead the chart card body is replaced with the empty-state copy block. The "Select at least one…" hint is shown inline in the affected chart card so the user can identify which filter to relax. |
| "Select all" / "Clear all" affordance | **Implicit only** — keyboard `Cmd-A` / `Ctrl-A` selects all options in a focused `<select multiple>` (browser native). No explicit "Select all" button. Rationale: each multi-select has at most ~12 options (11 scenarios, 7 envs, 4 allocators); explicit buttons add chrome that competes for attention with the data. The sidebar instruction (`Hold Cmd or Ctrl to multi-select. Charts update live.`) signals interactivity. |
| Focused option appearance | User-agent default + `outline: 2px solid #0969DA; outline-offset: 1px;` for the focused option only. Accent-color budget. |
| Hover state | User-agent default. We deliberately do not customize `<select>` hover — Chromium / Firefox / Safari / WebKit each style this slightly differently and overriding produces inconsistent screenshots. |
| Keyboard accessibility | Native `<select multiple>` is fully keyboard-accessible (Tab, arrow keys, Space to toggle, Cmd/Ctrl-A to select all). We add nothing on top. Skip-link to main content not needed for a single-page report. |
| State persistence | **None** — page reload returns to the all-selected default. No `localStorage` (the report may be opened from a `file://` URL where some browsers restrict storage; not worth the inconsistency). |
| Filter-state in URL | **Not in v1.** The report is a snapshot artifact; sharing a "view" of it is done by screenshot. `?scenarios=multithread,web` deep-linking is a v2 idea, deferred. |

### A/B picker (Config A / Config B for chart 4)

| Behavior | Specification |
|----------|---------------|
| Element | Two `<select>` (single-select, NOT multi) per config — one for allocator, one for env. Four `<select>` total. |
| Default A | (alphabetically-first allocator) + (alphabetically-first env) |
| Default B | (alphabetically-second allocator) + (same env as A) — so the first impression of the diff chart is "allocator-only difference, holding env fixed" |
| Disallowed selections | If A and B end up identical (same allocator, same env), render the diff chart with all bars at 0% and an inline note: `Config A and Config B are identical — pick differing values to see a delta.` |
| Suspect Config | If either Config A or Config B is a suspect run, the picker option label gets the `⚠` prefix per the suspect-badge contract; the diff chart adds a banner: `⚠ One or both selected configs are flagged suspect. See tooltip.` |

## Mermaid Theme Contract

> Mermaid diagrams appear in two places: REPORT.md (D-11, four allocator-architecture diagrams) and README.md (D-13, one system diagram). Both render server-side via GitHub-flavoured-markdown viewers (GitHub web, GitLab, VS Code preview); we do NOT bundle Mermaid.js into our `report/index.html`.

| Property | Value |
|----------|-------|
| Mermaid theme | `default` (no explicit `%%{init:…}%%` directive) — uses the renderer's chosen theme (light on github.com web, follows IDE theme in VS Code preview) |
| Diagram type | `flowchart TD` for all five diagrams (4 allocator + 1 system) — top-down for vertical scrolling in a markdown reader |
| Node style | unstyled — rely on Mermaid's defaults so the output renders identically across GitHub, GitLab, VS Code, Bitbucket. Avoid `classDef` color directives that produce inconsistent fallbacks. |
| Subgraph usage | Each allocator diagram uses one outer `subgraph` per allocator (per ARCHITECTURE.md §"Mermaid diagrams" reference); the system diagram in README.md does NOT use subgraphs (8 nodes flat). |
| Node count budget | Allocator diagrams: 10–15 nodes (D-11). System diagram: ~8 nodes (D-13). |
| Edge labels | Plain text only — no markdown, no HTML. Mermaid's parser is conservative; rich-text edges break the GitHub renderer. |
| Source location | Diagrams live as `&'static str` constants in `crates/alloc-bench-aggregator/src/diagrams.rs` (D-11). Aggregator emits them verbatim into REPORT.md; README.md is hand-edited (D-13). |

**Why no Mermaid styling:** the diagrams are read in many contexts (GitHub PR review, locally rendered, mobile GitHub app, screenshots embedded in slides). The default theme is the only one guaranteed to render consistently across all of those. Custom colors via `style A fill:#…` produce a different look in GitHub Dark mode versus GitHub Light versus VS Code, which causes screenshot drift across reviewers.

## Print and Screenshot Friendliness

> The report is frequently screenshotted and pasted into PR reviews, design docs, and Slack threads. The visual contract must survive bitmap capture without subtle drift between viewers.

| Concern | Decision |
|---------|----------|
| Default rendering | Light mode only in v1. Dark-mode deferred to v2 (rationale in Color section). |
| Page width for canonical screenshot | 1440px — locks the 2-column chart grid layout. PR screenshots taken at this width are portable across viewers. |
| Web fonts | None bundled — system stack (see Typography). A Slack-pasted screenshot rendered on a Windows reviewer's machine looks identical to the macOS author's because both fall through the same system stack to a Helvetica/Arial-class face. |
| Plotly fonts | Override `layout.font.family` to system stack (Plotly otherwise loads Open Sans webfont, which would make the in-chart text sometimes Open Sans, sometimes a fallback — visible drift). |
| Print stylesheet | `@media print { aside.sidebar { display: none; } main.charts { width: 100%; grid-template-columns: 1fr 1fr; } }` so a Save-As-PDF produces a sensible 2-up chart layout without sidebar chrome. |
| Plotly toolbar | Hidden on screenshot via `displayModeBar: false` in Plotly config OR enabled but with `displaylogo: false` and `modeBarButtonsToRemove: ['sendDataToCloud']`. Recommendation: **toolbar visible (`displayModeBar: 'hover'`)** — readers exploring the report locally benefit from zoom / pan / download-as-PNG; the toolbar fades away when the cursor leaves the chart, so screenshots taken without hovering are clean. |
| Page background for transparent screenshots | `#FFFFFF` (Dominant) — matches GitHub / Notion / Slack message backgrounds; pasted screenshots blend rather than show as a card-on-card. |
| Anti-aliasing of chart text | rely on browser default; do NOT set `text-rendering: geometricPrecision` (fights subpixel AA on macOS Retina). |

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|
| shadcn official | none | not applicable — phase does not use shadcn (no React/Next.js/Vite; native HTML emitted by Rust) |
| Plotly.js (CDN, single script tag) | one external script: `https://cdn.plot.ly/plotly-{PINNED_2.X}.min.js` | **plan-phase pins the exact `2.x.y` version** (per "Specifics" §"Plotly.js CDN URL pinned to a specific 2.x version"); aggregator emits a `<!-- plotly: 2.x.y · checksum: sha384-… -->` comment plus a `<script integrity="sha384-…" crossorigin="anonymous">` SRI attribute on the CDN tag so a CDN compromise is detected. Recommended: `plotly-2.35.0.min.js` (current stable as of May 2026); plan-phase confirms latest stable on the day of plan. |
| Mermaid (server-side via GitHub renderer) | not bundled | not applicable — no client-side Mermaid runtime |

**Why no third-party shadcn registry:** there is no shadcn project. The static-HTML output is fully under our control; no third-party UI components enter the page beyond Plotly.js (audited above with SRI integrity).

**SRI requirement is mandatory.** Without `integrity=` on the Plotly CDN tag, a compromised cdn.plot.ly could inject arbitrary JS into a developer's `file://` view of the report. SRI converts the CDN dependency into a content-addressed reference: a CDN swap is a hard-fail in the browser instead of a silent compromise. Plan-phase fetches the published Plotly 2.x.y SHA-384 from cdn.plot.ly's documented release page and bakes it into the template constant.
